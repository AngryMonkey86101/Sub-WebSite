# Диспетчер в РФ

Программа для вашего VPS в России. Она проверяет из РФ, доступен ли сервер VPN, и если IP заблокировали — через API хостера заказывает новый VPS, переносит туда VPN, направляет на него прежние имена DuckDNS и удаляет заблокированный сервер. План и этапы — [docs/PLAN.md](../docs/PLAN.md), раздел 15.

Готово: **шаг 0** (проверка API Zomro) и **этапы 1–3** — диспетчер работает как служба, раз в минуту проверяет сервер из РФ и пишет вам в Telegram, раз в час забирает свежий бэкап. Сам переезд (этапы 4–5) — следующий.

## Установка (этапы 1–3)

Нужны: VPS в РФ с Ubuntu, портал на сервере VPN — обновлённый до версии с диспетчером (server/README.md, обновление).

**1. На VPS в РФ под root — Docker и проект:**

```bash
apt-get update && apt-get install -y git docker.io docker-compose-v2
```
```bash
[ -d ~/sub-website/.git ] && git -C ~/sub-website pull || git clone --depth 1 https://github.com/AngryMonkey86101/Sub-WebSite.git ~/sub-website
```

**2. Настройки:**

```bash
cd ~/sub-website/dispatcher && cp -n .env.example .env && chmod 600 .env && nano .env
```

Заполните `PORTAL_HOST` (имя портала, как в браузере, без `https://`), `TELEGRAM_BOT_TOKEN` (тот же бот, что у портала) и `TELEGRAM_CHAT_ID` (админка портала → «Telegram» → «id чата»). Диспетчер сообщения боту только отправляет, портал по-прежнему сам их читает — друг другу они не мешают.

**3. Запуск:**

```bash
cd ~/sub-website/dispatcher && docker compose up -d --build
```

Если сборка не может скачать образ Node (Docker Hub из РФ бывает недоступен) — допишите в `.env` строку `NODE_IMAGE=mirror.gcr.io/library/node:22.23.4-alpine3.24` и повторите.

При первом запуске диспетчер создаёт свои ключи и присылает в Telegram две строки — `DISPATCHER_AGE_RECIPIENT=…` и `DISPATCHER_SSH_KEY=…`. Их же показывает команда:

```bash
cd ~/sub-website/dispatcher && docker compose exec dispatcher node src/cli.js keys
```

**4. На сервере VPN — доступ диспетчера к бэкапу:**

Под deploy допишите обе строки в `~/family-vpn/.env` и пересоберите портал — бэкап станет шифроваться и ключом диспетчера:

```bash
cd ~/family-vpn && nano .env && docker compose up -d --build
```

Под root разрешите ключу диспетчера одну-единственную команду — получить бэкап:

```bash
bash /home/deploy/family-vpn/scripts/install-dispatcher-key.sh
```

**5. Проверка — на VPS в РФ:**

```bash
cd ~/sub-website/dispatcher && docker compose exec dispatcher node src/cli.js backup
```
```bash
cd ~/sub-website/dispatcher && docker compose exec dispatcher node src/cli.js status
```

Должно быть «✓ Бэкап получен и проверен» и «Сервер … из РФ: доступен».

### Что делает

- **Раз в минуту** проверяет из РФ: находится ли имя портала и отвечает ли `https://<портал>/healthz`. Перед этим — свой интернет (ya.ru, vk.com): если не открывается ничего, сервер не судит — иначе сбой сети в РФ выглядел бы как блокировка.
- **Недоступен 15 минут подряд** — «🔴 Из РФ сервер недоступен …», одно сообщение на весь простой. Вернулся — «🟢 … Был недоступен N мин». Сменился IP портала — подсказка про `trust-host`.
- **Раз в час** забирает бэкап по SSH и проверяет его своим ключом: расшифровывается, внутри `env`, `amnezia.json`, `portal.sqlite`. Хранит 48 последних в томе данных. Расшифрованное на диск не пишется. Свежего бэкапа нет 3 часа, а сервер доступен — «⚠️» с причиной.
- **Сообщения в Telegram.** Из РФ `api.telegram.org` часто недоступен, поэтому сообщение идёт так: сначала напрямую (после неудачи прямой путь не пробуется 30 минут); не вышло — через сервер VPN: диспетчер передаёт текст по SSH, и его отправляет бот портала; сервер недоступен — сообщение ложится в очередь на томе данных и уходит, как только появится связь с сервером (в том числе с новым после переезда), с пометкой «⏱ … задержано». Порядок сообщений сохраняется. Нужен портал на сервере с командой `relay` (обновление ниже).
- **Ключ SSH диспетчера на сервере** привязан к скрипту `scripts/dispatcher-command.sh` (`install-dispatcher-key.sh`): по нему нельзя открыть оболочку, выполнить другую команду или пробросить порт — только получить зашифрованный бэкап, заморозить портал для плановой смены, разморозить его и передать сообщение админу через бота. После переезда `restore.sh` прописывает ключ на новом сервере сам. Если портал на сервере уже прописан со старой командой — выполните `install-dispatcher-key.sh` ещё раз после обновления.

### Меню

Всё основное — из меню в терминале, под root на VPS в РФ:

```bash
bash ~/sub-website/dispatcher/menu.sh
```

Пункты выбираются цифрами, `0` — назад или выход, после каждого экрана Enter возвращает в главное меню:

1. **Состояние сервера** — доступен ли сервер из РФ, последний бэкап, портал (active/frozen), серверы и баланс Zomro.
2. **Время до переезда** — когда следующая плановая смена и когда заказывается новый сервер.
3. **Пинг до сервера за рубежом** — ICMP-пинг (мин/средний/макс, потери) и время ответа портала по HTTPS.
4. **Актуальные цены на тарифы** — все дата-центры Zomro, цена за день со скидками, наличие.
5. **Выбранный тариф** — дата-центр, тариф, цена, образ ОС, пределы ожидания сборки.
6. **Изменить тариф** — дата-центр → тариф (по цене) → проверка у Zomro и подбор образа Ubuntu для этого дата-центра → запись в `.env` (прежний — в `.env.before-tariff`) и перезапуск диспетчера.
7. **Переезд сейчас** — переезд на новый сервер в фоне (см. ниже), ход — из лога. Перед стартом — где заказать: по очереди хостеров или только у одного (например, только Aeza). Если переезд уже идёт — посмотреть ход или **отменить ожидание сборки**: бросить этот заказ и заказать у следующего хостера, либо отменить переезд совсем (пока сервер собирается — старый сервер ещё не тронут).
8. **Изменить время переезда** — `ROTATION_TIME`, по Москве.
9. **Изменить период переезда** — `ROTATION_DAYS`, от 1 до 30 дней.
10. **Хостеры** — кто основной, кто запасной (`CLOUD_ORDER`), ключ API Aeza, разведка Aeza, пробный заказ у любого хостера.
11. **Удаление серверов** — все серверы у всех хостеров; выбранный ставится в очередь на удаление (см. ниже).
12. **Плановая смена: включить или выключить** — `ROTATION_ENABLED`. Выключена — сервер работает, пока его не заблокируют; переезд — по вашей команде (пункт 7) или аварийный.

### Хостеры: Zomro и Aeza

**Режим хостера.** `auto` — хостер участвует и в автоматических переездах (смена по расписанию, авария), `manual` — только в переезде по вашей команде. По умолчанию Zomro — `auto`, Aeza — `manual` (почасово втрое дороже): переезд к Aeza — пункт 7 → «только Aeza» или «по очереди». Сменить — пункт 10 → 6 (`AEZA_MODE`, `ZOMRO_MODE`).

Серверы заказываются у основного хостера; не собрался за отведённое время (у Zomro бывает часами) или нет денег — заказ удаляется и уходит запасному. Очередь — `CLOUD_ORDER` (по умолчанию `zomro,aeza`, в меню — пункт 10). Хостер без настроек в очереди пропускается.

**Aeza** — API v2 `https://my.aeza.net/api/v2`, ключ — личный кабинет Aeza → «API», в `.env` — `AEZA_API_KEY` (в меню: пункт 10 → 2, ключ на экране не появится). Тариф — пункт 6 (сначала хостер); оплата по умолчанию почасовая (`AEZA_TERM=hour`), удалённый сервер дальше не оплачивается. Пароль root задаётся после сборки (`change-password`). У новых аккаунтов Aeza есть лимиты на почасовые серверы (wiki.aeza.net → «Раздел лимитов»): если заказ отклонён — пополните баланс или напишите в поддержку.

Разведка на живом аккаунте показала: цены и баланс в API — в центах (диспетчер переводит в EUR); у многих тарифов нет почасовой оплаты — только месяц и дольше. Такой тариф для смены сервера раз в несколько дней не годится (каждый новый сервер — оплата за месяц), поэтому в меню он помечен «нет оплаты за час» и не выбирается. Сначала — **разведка** (только чтение, пункт 10 → 3, или `aeza-probe`): она покажет тарифы с почасовой оплатой и расчёт цены заказа; затем — **пробный заказ** (пункт 10 → 4).

Почасовые тарифы на 14.11.2026: самые дешёвые — Shared (1 vCPU, 2 ГБ, 30 ГБ) по 0,04 EUR в час, около 0,96 EUR в сутки; Dedicated — 0,05 EUR в час. Это дороже Zomro (0,29–0,36 EUR в сутки), поэтому Aeza удобна запасным хостером. Лимит нового аккаунта — один сервер каждого типа; после пополнений на 10 EUR суммарно — два (нужно, если и старый, и новый сервер — у Aeza).

### Отмена ожидания сборки

Пока переезд или пробный заказ ждёт, когда хостер соберёт сервер, ожидание можно прервать — меню (пункт 7 во время переезда, пункт 10 → 5 для пробного заказа) или командой `cancel-wait`:

- `cancel-wait` — бросить этот заказ: переезд заказывает у следующего хостера из `CLOUD_ORDER` (если следующего нет — переезд отменяется);
- `cancel-wait --all` — отменить переезд или пробный заказ совсем.

Ждущий процесс замечает просьбу в течение 15 секунд. Брошенный сервер ещё собирается, удалить его хостер не даёт — он встаёт в очередь на удаление (пункт 11) и удаляется после сборки. Просьба живёт 10 минут и не действует на ожидание, начатое позже. Когда сервер уже собран и переезд пошёл дальше (подготовка, заморозка, перенос), отменять ожидание нечего — сбой на этих шагах откатывается сам.

### Очередь на удаление

Пункт 11 (или `delete-queue add ХОСТЕР НОМЕР`): выбранный сервер служба удаляет, как только хостер позволит. Пока сервер собирается, ни Zomro, ни Aeza удалить его не дают — служба проверяет раз в 10 минут и удаляет после сборки; в меню видно состояние каждого сервера в очереди и последняя ошибка. Сервер, созданный не диспетчером, ставится в очередь только после отдельного предупреждения (`--foreign`); рабочий сервер (на котором сейчас портал) в очередь не ставится. Сервер исчез у хостера (удалили в кабинете) — запись снимается сама.

### Переезд

Команда `migrate --yes` (в меню — пункт 7) переносит портал, бота, ключи VPN и имена DuckDNS на новый сервер. Ключи у семьи не меняются — достаточно выключить и включить VPN.

1. Заказ сервера у Zomro по выбранному тарифу, ожидание сборки (`ZOMRO_BUILD_MIN`) и SSH.
2. Подготовка заранее: на новом сервере — код проекта из GitHub (`REPO_URL`, ветка `REPO_REF`) и `restore.sh --prepare` с последним бэкапом. Старый сервер в это время работает как обычно.
3. Заморозка старого (`freeze`): бот, оплаты, сторож DuckDNS и сайт — на паузе, VPN работает; финальный бэкап и сертификаты Caddy. Если из РФ старый сервер уже заблокирован — диспетчер идёт к нему **через новый сервер** (из-за рубежа он виден). Если старый не отвечает и оттуда — переезд с последнего бэкапа (изменения за последний час могут потеряться).
4. `restore.sh --finish` на новом: база, портал, имена DuckDNS, Caddy с прежними сертификатами.
5. Проверка из РФ, `trust-host`, бэкап уже с нового сервера.
6. Старый сервер: созданный диспетчером — удаляется через `MIGRATE_KEEP_OLD_H` часов (по умолчанию 2: семья успевает переподключиться); созданный не им (например, первый, настроенный вручную) — не удаляется, придёт сообщение: удалите в кабинете или `remove ID --yes --foreign`.

Сбой до переноса имён — откат: старый сервер размораживается, новый удаляется. Сбой на переносе имён — без отката (иначе было бы два бота): громкое сообщение. Пока идёт заморозка и перенос, монитор не шлёт ложных «🔴». Одновременно идёт только один переезд.

**Безопасность.** Бэкап уходит на новый сервер перешифрованным разовым ключом age — закрытый ключ диспетчера туда не попадает. На время переезда открытый SSH-ключ диспетчера лежит у root нового сервера (через него — путь к старому), в конце он убирается. Пароль root нового сервера задаётся при заказе и хранится в томе диспетчера (`servers/`, только для root): `root-password`.

Плановая смена по расписанию (пункт 2 меню) — следующий этап: пока переезд — по команде.

`docker compose exec dispatcher node src/cli.js <команда>` в `~/sub-website/dispatcher`:

| `zomro-test --yes` | Пробный заказ у Zomro: заказать сервер, дождаться IP, войти по паролю root, удалить. Несколько центов с баланса |

**Обновление:** `git -C ~/sub-website pull && cd ~/sub-website/dispatcher && docker compose up -d --build`. Ключи, бэкапы и состояние — в томе `dispatcher_data`, при обновлении не теряются.

**Что лежит на диспетчере:** закрытый ключ age диспетчера (расшифровывает бэкап — а в нём ключи сервера VPN, токен бота, ключи ЮKassa) и закрытый SSH-ключ. Держите VPS диспетчера закрытым: вход по SSH только по ключу, лишнего на нём не запускайте. Если диспетчер скомпрометирован — удалите на сервере VPN строки `DISPATCHER_*` из `.env`, пересоберите портал и выполните `install-dispatcher-key.sh` (доступ уберётся), затем удалите том диспетчера (`docker compose down -v`) и поставьте заново — ключи будут новые. Ваш ключ age от этого не зависит.

## Zomro: заказ и удаление серверов (этап 4)

Диспетчер заказывает серверы VPN у Zomro через API — под вашим логином. Впишите в `.env` диспетчера:

```bash
cd ~/sub-website/dispatcher && nano .env
```

строки `ZOMRO_USER=` (логин кабинета) и `ZOMRO_PASSWORD=` (пароль), затем `docker compose up -d --build`. Тариф, дата-центр и ОС уже выбраны по проверке API: `7864` «Starter AMD | NL-3 v.3» (0,36 EUR в день), Нидерланды, Ubuntu 24.04. Дешевле — `7920` «Blitz Intel | NL-3» (0,31 EUR), но на живом аккаунте его серверы собирались часами, а один за 12 часов так и не собрался — поменять можно строками `ZOMRO_PRICELIST`, `ZOMRO_DATACENTER`, `ZOMRO_OS` (подсказки — в `.env.example`).

**Пробный заказ** — проверка на живом аккаунте того, что без денег не проверить. Zomro собирает сервер долго, поэтому тест запускается в фоне (обрыв SSH-сессии его не прервёт), а вывод смотрится отдельно:

```bash
cd ~/sub-website/dispatcher && docker compose exec -d dispatcher sh -c 'node src/cli.js zomro-test --yes > /data/zomro-test.log 2>&1'; sleep 3; docker compose exec dispatcher tail -F /data/zomro-test.log
```

Выход из просмотра — Ctrl+C, тест продолжается; итог придёт и в Telegram. Диспетчер закажет сервер `family-vpn-…` посуточно, дождётся IP, войдёт по паролю root (пароль задаётся при заказе, нигде не показывается) и удалит сервер. Оплата у Zomro почасовая — обойдётся в несколько центов. Если что-то сломается после заказа, сервер всё равно удаляется; если не удалился — придёт «⚠️ … Удалите его в кабинете Zomro».

**Долгая сборка.** Сервер ждут до 90 минут (`ZOMRO_BUILD_MIN`), затем ещё до 20 минут — пока откроется SSH (`ZOMRO_SSH_MIN`); раз в 5 минут в выводе — «… собирается N мин, состояние …». Каждый заказ диспетчер записывает в учёт сразу после отправки. Если заказ не довели до конца — тест прервали, контейнер перезапустился, сервер появился в списке уже после того, как его перестали ждать, — служба раз в час находит такие серверы и удаляет сама: «🧹 Удалил брошенный сервер …». Записи учёта видны в `servers`.

**Безопасность.** Диспетчер удаляет только серверы с именем `family-vpn-…` — ваши остальные серверы у Zomro он видит, но не трогает. Пароль Zomro в `.env` позволяет тратить деньги с баланса: держите на балансе сумму на 1–2 месяца, а `.env` — только для root (`chmod 600 .env`).

## Шаг 0. Проверка API Zomro

Скрипт `scripts/zomro-probe.mjs` входит в API Zomro под вашим логином и **только читает**: ваши услуги, баланс, тарифы облачных VPS и поля формы заказа (дата-центры, образы ОС, периоды оплаты, в том числе посуточный). Ничего не заказывает, не останавливает и не удаляет.

Вывод можно прислать в чат целиком: пароля и ключа сессии в нём нет, почта, телефон, имена и адреса скрыты, IP-адреса укорочены до первого числа.

**На VPS в РФ под root:**

1. Нужны git и Node.js 18 или новее:
   ```bash
   apt-get update && apt-get install -y git nodejs && node -v
   ```
   Если `node -v` показывает меньше `v18` — запустите скрипт через Docker (пункт 3, второй вариант).
2. Скачайте проект (или обновите, если уже скачан):
   ```bash
   [ -d ~/sub-website/.git ] && git -C ~/sub-website pull || git clone --depth 1 https://github.com/AngryMonkey86101/Sub-WebSite.git ~/sub-website
   ```
3. Запустите проверку. Логин и пароль от личного кабинета Zomro вводятся с клавиатуры, пароль на экране не виден и в истории команд не остаётся:
   ```bash
   read -rp 'Логин Zomro: ' ZOMRO_USER && read -rsp 'Пароль Zomro: ' ZOMRO_PASSWORD && echo && export ZOMRO_USER ZOMRO_PASSWORD && node ~/sub-website/dispatcher/scripts/zomro-probe.mjs; unset ZOMRO_USER ZOMRO_PASSWORD
   ```
   Через Docker, если Node.js старый:
   ```bash
   read -rp 'Логин Zomro: ' ZOMRO_USER && read -rsp 'Пароль Zomro: ' ZOMRO_PASSWORD && echo && export ZOMRO_USER ZOMRO_PASSWORD && docker run --rm -e ZOMRO_USER -e ZOMRO_PASSWORD -v ~/sub-website/dispatcher:/app:ro -w /app node:22.23.4-alpine3.24 node scripts/zomro-probe.mjs; unset ZOMRO_USER ZOMRO_PASSWORD
   ```
4. Пришлите вывод в чат.

**Точечный запрос.** Чтобы проверить одну функцию API, а не всё сразу, — после `node …/zomro-probe.mjs` допишите `call ФУНКЦИЯ параметр=значение`, например:

```bash
read -rp 'Логин Zomro: ' ZOMRO_USER && read -rsp 'Пароль Zomro: ' ZOMRO_PASSWORD && echo && export ZOMRO_USER ZOMRO_PASSWORD && node ~/sub-website/dispatcher/scripts/zomro-probe.mjs call v2.instances.order.pricelist datacenter=1; unset ZOMRO_USER ZOMRO_PASSWORD
```

Это тоже только чтение: функции, которые могут что-то изменить (удаление, остановка, оплата, подтверждение заказа и т. п.), скрипт не вызывает, а параметр `sok` отбрасывает.

**Если не получилось:**

- «Zomro недоступна (…)» — VPS в РФ не достучался до `api.zomro.com`. Проверьте: `curl -sI https://api.zomro.com/ | head -1`.
- «ответила не JSON … проверьте адрес API» — у API другой адрес. Если знаете его (кабинет Zomro → раздел про API), задайте перед запуском: `export ZOMRO_API_URL=https://…/billmgr`.
- «Войти не удалось» — неверный логин или пароль, либо включена двухфакторная авторизация: тогда вход по API может требовать отдельный ключ — посмотрите в кабинете Zomro, есть ли «ключи API» или отдельный пользователь для API.
